# Case study (draft)

The write-up of this project. Filled in as results land; nothing here is claimed until the journal has the number behind it.

## The problem

AI agents can now drive Blender, but the popular setups are expensive and imprecise: hundreds of tool descriptions sent on every turn, a screenshot as the only way to check work, and fragile scripts. For a commercial CGI artist who wants to hand off modeling and keep art direction, that cost and unreliability is the blocker.

## Approach

- Measured first: an eval suite of product-modeling tasks with automatic checks, and baselines across four existing agent setups.
- Pass / fail / void, so setup faults never count against a model.
- The checks are checked: each task ships with a reference model that must pass and deliberately broken versions that must fail exactly the checks they target. Even so, the very first real run exposed a check that would have failed valid work (it assumed one thread profile); it was fixed and the run re-scored before any number was used.
- Then a harness designed around where the baselines spent their tokens.

## Results

**Pilot (small sample; a pointer, not the finding).** Five product tasks, four setups, three repeats each, on Claude Haiku 5.5: 60 runs for $0.49 in total, none void. Per passed task, the agent writing its own scripts used about 22,500 tokens; Blender's official MCP server about 75,000; the popular community server about 70,000; and a 225-tool typed server about 1,000,000, passing 5 of 15 because, out of the box, the agent stops to ask the user to switch on Python. With Python switched on, as a user would, that server passed 14 of 15 at about 215,000 tokens per passed task: still about three times the other servers, because its tool menu rides along on every turn. Most of the gap is fixed overhead, not modeling: tool descriptions resent on every turn range from under 1,000 tokens to about 62,000.

**A prompt result, properly tested.** One extra paragraph asking for a clean mesh (no duplicate vertices or zero-area faces) took the duplicate-vertex defect from 7 in 50 runs to 0 in 50 (p = 0.006), and the pass rate from 36/50 to 47/50, at 15% fewer tokens. The first test, at 20 a side, pointed the same way but wasn't significant. It was rerun at a larger sample rather than adopted on a hunch.

**Baselines (the finding).** 30 product-modeling tasks (hard-surface parts, client revisions, layouts, long multi-part builds), four setups, three repeats each: 360 runs on Claude Haiku 5.5, none void, $2.77 in total. Every setup passed about 90% of tasks (80 to 82 of 90), so they are equally accurate and differ only in cost. Per passed task, the agent writing its own scripts used about 26,700 tokens; the popular community server about 78,000 (2.9×); Blender's official server about 87,000 (3.3×); the 225-tool server about 345,000 (12.9×). The gap is overhead, not modeling: tool definitions are 90% of the 225-tool server's input, 56% of the community server's and 38% of the official one's. With no MCP at all, the biggest cost is the model's own earlier reasoning replayed each turn (35%). Client revisions cost the most on every setup, because the agent has to read the existing model before it can change it.

**Harness v1 (development suite).** A harness built from that breakdown: one tool on a Blender session that stays open, a compact scene report after every call in place of the agent's own inspection code, the existing model read once up front, generic modeling helpers, and a run that ends as soon as a call marked final comes back clean, instead of a closing turn that resends everything. On the same 30 tasks × 3 it passed 82 of 90 (91%, against 80 for the best baseline) at 9,773 tokens per passed task: 37% of no MCP's 26,727, past the target of half. Runs took half the wall time (15 s against 32 s) and half the cost. Getting there took four versions, and two of the fixes were to my own harness: a report in millimetres that agents read as metres (they built models 1,000× too large), and a unit constant so they stop writing millimetre figures as metres. **Held-out confirmation, run once.** On 8 tasks never used during development, the harness passed 20 of 24 (no MCP: 19) and used 58% fewer tokens on the typical task (geometric-mean ratio 0.42), but only 34% fewer per passed task overall (37,958 against 57,864), short of half. The difference is a tail: two runs got stuck repairing a problem the scene report kept flagging, 13 and 14 calls long, and held half the harness's tokens. The same gate that keeps output correct can trap an agent that can't fix what it's told about. It's reported as measured.

**Why the agent got stuck, and the fix (h5).** Reading the stuck runs showed both causes were partly my harness's fault. My cleanup helper was 100× stricter than my own report about what counts as a degenerate face, and the report gave a count without a location, so the agent hunted for faces it couldn't find. On the lamp, the agent turned a cylinder on its side by swapping two coordinates, which mirrors the mesh inside out, so the boolean silently cut no hole; it then decided the intersection warning was a false alarm. h5 aligned the thresholds, put locations on the problems, made the boolean helper fix inside-out cutters, and added a backstop for runs that still loop. Replaying the recorded stuck runs through h5 took every one of them from 6–14 calls to 1–3, each passing. On the development suite h5 passed 79 of 90 at 8,202 tokens per pass, 31% of no MCP.

**Second held-out set, run once.** On 8 new tasks, h5 passed 24 of 24 (no MCP: 22) at 3,451 tokens per passed task against 15,392: 22%, and 27% on the typical task, with every run finished in one tool call at a third of the wall time. An independent review reproduced every figure, and pointed out that this set came out much easier than the first (the baseline needed a quarter of the tokens it needed there), so the two held-out results are reported together: harder tasks, 0.66 overall and 0.42 typical; easier tasks, 0.22 and 0.27. All of Phase 3 cost under a dollar, on the cheapest model.

**Turning thinking off doesn't save tokens.** Thinking is most of what a small model writes, so I measured it switched off, on both the harness and the no-MCP baseline (180 runs, $0.35). Each call got shorter, but agents needed more calls and passed less often. The baseline collapsed from 89% to 59% passing; the harness held 83%, but used 25% more tokens per passed task (10,212 against 8,202). Simple layouts got cheaper without thinking, while long multi-part builds doubled in cost. The reasoning was earning its place, so it stays on. Keeping thinking but resending only the latest call's reasoning (another 180 runs) halved replay, but agents took slightly more calls without their earlier reasoning: 11% fewer tokens per pass for no MCP and 4% for the harness, both inside the noise. It also broke prompt-cache reuse, so cost went up. Neither change is in the headline.

**Third held-out set, as hard as the development suite (h6), run once.** I fixed the review's code issues in h6, proved each fix against a live Blender, replayed all 408 recorded runs through it for free (no pass lost), and froze it. Only then did agents write eight new tasks at development difficulty: fillets, tapers, tilted features, patterns, and revisions that need the model read. Two independent builders then remade every task from its prompt alone, a different way, to check the grading was fair; that caught one real defect, which I fixed before anything ran. Both setups passed 18 of 24. The headline came out at 0.12, but I don't claim it: one revision defeated both setups and cost the baseline up to 1.6 million tokens a run, 84% of its total. Without that task the result matches the first hard set almost exactly: 0.63 overall and 0.43 on the typical task (first set: 0.66 and 0.42). On hard, unseen work the harness is reliably about 2.3× cheaper on the typical task, and runs in under half the wall time; what holds the overall figure back is its own long runs, now mostly on revisions.

**Where the next saving is, found in the traces.** Mining 181 recorded revision runs showed 40% of their calls are the agent reading the existing model before its first edit, up to 45% of revision tokens. 205 of those 210 calls rebuild four kinds of fact my opening scene read doesn't give: where the holes are, how repeated features are spaced, which radius sits at which height, and each flat level's outline. On the three revisions where the read already covered the edit, agents didn't inspect at all. That turns the next version into a targeted change, with a measured ceiling, rather than a guess.

**Giving the agent the facts it went looking for (h7).** I added exactly those four facts to the opening read, each computed the same way for any mesh: a revolved part's outline in the form the lathe helper takes, round holes and posts with their positions, repeated features with count, spacing and one instance's size, and each flat level's outline with its corner radius. Built and checked for free first (every starting scene, 400 agent-built scenes, a replay of all 114 recorded h6 runs with no pass lost), it adds about 65 tokens per task. On the development suite h7 passed 86 of 90, the best of any setup (no MCP: 80), at 6,489 tokens per passed task: 24% of no MCP's, against 37% for h6, and 0.29 on the typical task. Revisions, the costliest group on every setup, went from 21,908 tokens per pass to 5,174, and agents went from 1.8 inspection calls per revision to almost none (1 in 24 runs). Builds, which the read doesn't touch, stayed within noise. Runs take 12 seconds against no MCP's 32. A fresh held-out set comes next before this is claimed.

**Fourth held-out set (h7), run once.** I froze h7, and only then did agents write eight new tasks at development difficulty. The authors were kept away from the harness code, so the tasks couldn't be shaped around the new read. Two independent builders then remade every task from its prompt alone, a different way each, and all 16 builds passed. On the run, h7 passed 20 of 24 (no MCP: 18) at 11,934 tokens per passed task against 58,147: 21%, and 27% on the typical task, in half the wall time. No task defeated both setups, so nothing is excluded. One revision did cost the baseline up to 291k tokens a run, and the result holds without it: 32% overall and 34% typical. On the earlier hard held-out sets the same figures were about 0.65 overall and 0.42 typical. So h7's gain on revisions carries to work it has never seen, and the whole held-out run cost 19 cents.
